## 追加1【重要】Net Delta 管理

### 背景と問題

現状の設計は、**建てる瞬間の両建て成立**（`HedgeState` による同時発注と片肺クローズ）は扱っているが、**保有中にデルタがずれていくこと**を扱っていない。

両建ては理想的には以下の状態を保つ。

```
Hyperliquid = +0.500 BTC
Lighter     = -0.500 BTC
Net Delta   =  0.000 BTC
```

しかし実際には以下の要因でずれる。

- **部分約定の端数**: 両DEXで最小注文単位・価格刻みが異なるため、完全に同数量にならない
- **決済時の端数**: 一部だけ決済された場合
- **強制決済・ADL**: 片方のDEXで自動デレバレッジが発動した場合
- **数量の丸め**: `Decimal` を各DEXの精度に丸める際の差

```
Hyperliquid = +0.500 BTC
Lighter     = -0.497 BTC
Net Delta   = +0.003 BTC   ← 実質的な方向性ポジション
```

**ファンディング裁定では特に深刻。** 数時間〜数日保有するため、わずかなずれが長時間の価格変動リスクに晒される。「市場中立のつもりで方向性リスクを持っている」状態は、この戦略で最も避けたい失敗である。

### 設計方針

`risk` crate に **Position Manager** を追加し、両DEXの実ポジションを定期的に照合してデルタを監視する。

**重要**: 監視対象は「botが記録している想定ポジション」ではなく、**各DEXのAPIから取得した実ポジション**であること。想定と実際が乖離していること自体が検知すべき異常である。

### データ構造

```rust
/// 銘柄ごとのネットデルタ状態
#[derive(Debug, Clone)]
pub struct NetDeltaStatus {
    pub symbol: Symbol,
    /// DEXごとの実ポジション（DEX APIから取得した値。ロングが正）
    pub positions: HashMap<Dex, Quantity>,
    /// 全DEX合計のネットポジション
    pub net_delta: Quantity,
    /// ノーショナル換算のネットデルタ（USD）
    pub net_delta_usd: Decimal,
    /// botが記録している想定ポジションとの差
    pub drift_from_expected: HashMap<Dex, Quantity>,
    pub checked_at_wall_ms: u64,
}
```

### 監視ループ

`risk` の watchdog タスク内で定期実行する（キルスイッチと同じく、Market Data / Execution から独立していること）。

```
定期実行（設定間隔ごと）
 ├─ 各DEXの実ポジションをAPIで取得
 ├─ 銘柄ごとに合算し net_delta を算出
 ├─ bot の想定ポジションと比較し drift を算出
 └─ 閾値判定
     ├─ 許容範囲内 → 何もしない
     ├─ 警告閾値超過 → ログ + 通知
     └─ 是正閾値超過 → リバランス発注
```

### 閾値の設計

**絶対数量ではなくノーショナル（USD）で判定すること。** BTC 0.003 と HYPE 0.003 では意味が全く違う。

```toml
[risk.net_delta]
enabled = true
# 実ポジションの照合間隔（秒）
check_interval_secs = 60
# 警告のみ（ログ + 通知）
warn_threshold_usd = 50
# 自動リバランスを発動する閾値
rebalance_threshold_usd = 200
# これを超えたら全ポジション解消（キルスイッチ）
critical_threshold_usd = 1000
# botの想定ポジションと実ポジションの乖離許容値
# これを超えたら状態不整合として新規発注を停止する
max_drift_usd = 100
```

### リバランス処理

デルタが `rebalance_threshold_usd` を超えた場合、**不足している側に差分だけ発注**して中立に戻す。

```rust
// 例: Hyperliquid +0.500 / Lighter -0.497 → net +0.003
// → Lighter で 0.003 追加ショート（または Hyperliquid で 0.003 決済）
```

**リバランス時の注意点**:

- 発注先の選択: **板が厚い方**、または**手数料が安い方**を選ぶ。設定で切り替え可能にすること
- 最小注文単位を下回る差分は是正できない。この場合は**警告のみに留め、無理に発注しない**（発注エラーを繰り返すだけになる）
- リバランス自体にも手数料とスリッページがかかる。**閾値を低くしすぎると、リバランスのコストがファンディング収益を食う**。`warn_threshold_usd` と `rebalance_threshold_usd` の間に十分な幅を持たせること
- リバランス発注も `HedgeState` と同様に約定確認を行い、失敗したら再試行・エスカレーションすること

### 想定ポジションとの乖離（drift）の扱い

`net_delta` とは別に、**「botが持っているつもりの数量」と「実際の数量」の差**を監視する。

これが大きい場合、以下の異常を示唆する:

- 約定通知の取りこぼし（WS切断中に約定した）
- 強制決済・ADLの発生
- 状態永続化の不整合（クラッシュ後の復元漏れ）

**drift が `max_drift_usd` を超えたら、新規発注を停止する。** 自分のポジションを正しく把握できていない状態で発注を続けるのは危険。人間の確認を待つ（ソフト停止）。

### キルスイッチとの統合

既存の多層キルスイッチ（`dual-strategy-design.md` §7）に、Net Delta 起因の発動条件を追加する。

| 条件 | 動作 |
|---|---|
| `net_delta_usd > warn_threshold` | ログ + 通知のみ |
| `net_delta_usd > rebalance_threshold` | リバランス発注 |
| `net_delta_usd > critical_threshold` | **ハード停止**（全ポジション解消） |
| `drift_usd > max_drift_usd` | **ソフト停止**（新規発注のみ停止、人間の確認待ち） |
| リバランスが規定回数連続で失敗 | ソフト停止 |

### ログ・記録

Net Delta の状態は定期的にCSVに記録する。フェーズ2以降で「どれくらいデルタがずれるものなのか」を実測するため。

**ファイル**: `data/{YYYY-MM-DD}_net_delta.csv`

| カラム | 説明 |
|---|---|
| `timestamp_ms` | 照合時刻 |
| `symbol` | 銘柄 |
| `pos_hyperliquid` / `pos_lighter` / ... | DEXごとの実ポジション |
| `net_delta` | ネットポジション（数量） |
| `net_delta_usd` | ノーショナル換算 |
| `drift_usd` | 想定との乖離 |
| `action` | none / warned / rebalanced / halted |

### 追加すべきテスト

1. 両DEXのポジションが完全に相殺していれば `net_delta` がゼロになること
2. 片方が少ない場合に正しく符号付きで `net_delta` が算出されること
3. ノーショナル換算が正しいこと（価格を掛けている）
4. 各閾値で期待するアクションが選択されること（warn / rebalance / halt）
5. 最小注文単位を下回る差分ではリバランス発注を行わないこと
6. drift が閾値を超えたらソフト停止になること
7. **想定ポジションが正しくても実ポジションがずれていれば検知されること**（想定値だけ見ていたら気づけないケース）

## 追加2 Open Interest と取引量の収集

### 背景

現状のフェーズ1では板データとファンディングを収集しているが、**Open Interest（未決済建玉）と取引量**を取っていない。

これらは以下の判断に使える:

- **見かけの流動性と実需の乖離**: 出来高に対してOIが極端に小さい場合、ポイント稼ぎ目的の回転売買が出来高を膨らませている可能性がある。板が想定より薄く、アービトラージの執行に耐えない
- **ファンディングレートの背景理解**: OIが偏っている（ロングに傾いている）DEXはファンディングが高くなる。レート差が持続するかの判断材料になる
- **銘柄の選定**: OIが小さすぎる銘柄は、想定サイズが板を動かしてしまう

### 実装方針

**ファンディングと同じパイプラインに相乗りさせる。** Lighterの `market_stats` チャンネルには既にこれらが含まれている可能性が高く、Hyperliquidも同様のチャンネルで取得できる見込み。**新規のWS接続は増やさないこと。**

`FundingRate` 構造体を拡張するか、並列の `MarketStats` 構造体を追加する。

```rust
#[derive(Debug, Clone)]
pub struct MarketStats {
    pub dex: Dex,
    pub symbol: Symbol,
    /// 未決済建玉（契約数量）
    pub open_interest: Option<Quantity>,
    /// 直近24時間の取引量（USD建て）
    pub volume_24h_usd: Option<Decimal>,
    pub trace: MessageTrace,
}
```

### CSV出力

ファンディングCSVに列を追加するか、別ファイルにする。**更新頻度が近いならファンディングCSVに相乗りさせる方が分析しやすい**（同じ時刻の行に並ぶため）。

追加カラム:

| カラム | 説明 |
|---|---|
| `open_interest` | 未決済建玉 |
| `volume_24h_usd` | 24時間取引量 |
| `volume_oi_ratio` | 出来高 / OI。**高すぎる場合は回転売買の疑い** |

### 優先度

**追加1（Net Delta）より低い。** 取得できるDEXから順に実装すればよく、取れないDEXがあってもフェーズ1を止める理由にはならない。

## 補足: なぜ Net Delta 管理が必要か

`HedgeState` の片肺検知は「**建てる瞬間**」の保護であり、Net Delta 管理は「**保有し続けている間**」の保護である。両者は別物で、片方だけでは不十分。

価格差アービトラージは保有時間が秒〜分なので前者で概ね足りるが、**ファンディング裁定は数時間〜数日保有する**。その間にわずかなずれが蓄積し、気づかないうちに方向性ポジションを持っている、という状態が最も危険である。

「市場中立のつもりで方向性リスクを持っている」ことが、この戦略における最大の隠れたリスクになる。
