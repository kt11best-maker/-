| 項目 | 変更前 | 変更後 |

**ファンディング精算間隔を揃えることを最優先とした。** HyperliquidとLighterはともに1時間精算のため、ファンディングレートを直接比較でき、裁定の設計が単純になる。Asterは8時間精算のため間隔の正規化が必要になり、ポジション保有期間の設計も変わってしまう。

> **精算間隔は実装前に必ず一次情報で再確認すること。** 本書の記載も含め、DEXの仕様は変更されうる。

## 2. 2戦略の位置づけと共通基盤

### 2.1 2つの戦略の性質の違い

| 観点 | 価格差アービトラージ | ファンディング裁定 |
|---|---|---|
| 収益源 | DEX間の一時的な価格乖離 | DEX間のファンディングレート差 |
| 速度要求 | **極めて高い**（数十〜数百ms） | **低い**（数分〜数時間の判断で足りる） |
| ポジション保有時間 | 秒〜分 | 時間〜日 |
| 主なリスク | 片肺（Unhedged）、スリッページ | レート反転、証拠金維持、長期保有中の価格変動 |
| 執行方式 | IOC同時発注、即時クローズ | 指値でじっくり建てられる |
| キャパシティ | 板の厚さに強く制約 | 証拠金量に制約 |

**同じ配管（板データ、執行基盤、リスク管理）を共有しつつ、判定ロジックと執行方針を分ける**のが本設計の核。

## 3. strategy-traits（戦略の共通インターフェース）

2戦略が同じ執行基盤・リスク管理を使えるよう、共通のインターフェースを定義する。

```rust
/// 戦略が発するシグナル
#[derive(Debug, Clone)]
pub struct TradeSignal {
    pub strategy: StrategyKind,
    pub symbol: Symbol,
    /// ロングを建てる側
    pub long_dex: Dex,
    /// ショートを建てる側
    pub short_dex: Dex,
    /// 想定ノーショナル（USD建て）
    pub notional: Decimal,
    /// 期待収益（bps）。戦略により意味が異なる（下記参照）
    pub expected_profit_bps: Decimal,
    /// 執行の緊急度。執行方式の選択に使う
    pub urgency: Urgency,
    /// シグナル生成時点の根拠（ログ・分析用）
    pub rationale: SignalRationale,
    pub created_at: Instant,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum StrategyKind {
    PriceArb,
    FundingArb,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Urgency {
    /// 価格差アービトラージ用。IOCで即時執行、間に合わなければ諦める
    Immediate,
    /// ファンディング裁定用。指値でじっくり建てる。数分待ってよい
    Patient,
}

#[async_trait]
pub trait Strategy: Send + Sync {
    fn kind(&self) -> StrategyKind;
    /// 現在の市場状態からシグナルを評価する
    fn evaluate(&self, ctx: &MarketContext) -> Vec<TradeSignal>;
    /// 既存ポジションを解消すべきか判定する
    fn should_exit(&self, position: &OpenPosition, ctx: &MarketContext) -> Option<ExitReason>;
}
```

> **`expected_profit_bps` の意味の違いに注意**
> - 価格差アービトラージ: **1回の往復で得られる**純利益（bps）
> - ファンディング裁定: **1精算あたりの**純収益（bps）。年率ではない
>
> この2つを同じ土俵で比較してはいけない。資金配分を判断する際は、ファンディング側は「想定保有精算回数 × 1回あたり収益」に換算すること。混同すると資金配分が壊れる。

## 5. strategy-funding-arb（ファンディング裁定）

### 5.1 基本の考え方

同一銘柄について、ファンディングレートが**高いDEXでショート**、**低い（またはマイナスの）DEXでロング**を建てる。両建てなので価格変動リスクは相殺され、レート差を精算ごとに受け取る。

```
1精算あたりの粗収益(bps) = |rate_short_dex − rate_long_dex| × 10000
```

### 5.2 純収益の判定式

> **前提: 現物は使わない。perp同士の両建てのみで構成する**（資金効率のため）。したがって「現物ロング × perpショート」のキャッシュ&キャリーは本設計の対象外。

perp同士の両建てでは、価格差（ベーシス）は**利益源ではなく、エントリー・エグジットのコスト（またはボーナス）**として損益に効く。これを損益式に必ず含めること。

```
総損益(bps) = ファンディング差の累計（レート差 × 保有精算回数）
            + (エントリー時の価格差 − エグジット時の価格差)   ← ベーシス項
            − 手数料（建て往復 + 決済往復 = 両DEX計4回分）
            − スリッページ（建て・決済）
            − 安全マージン
```

**ベーシス項の意味**

両建てなので価格の絶対値は損益に無関係だが、**2 DEX間の価格差が建てた時と決済した時で変わると、その差分がそのまま損益になる**。

例: Hyperliquidが60,000、Lighterが60,030の時に「Hyperliquidロング × Lighterショート」を建てる。決済時に両者の価格が揃っていれば30の差は利益。逆に差が広がれば損失。

したがって:

- **ファンディング差が有利な方向と、価格差が有利な方向が一致するタイミングで建てるのが理想**
- ファンディング差が魅力的でも、価格差が不利な方向に開いている瞬間に建てると、数回分の精算収益が一撃で消えうる
- エグジットも同様に、価格差が有利に戻ったタイミングを狙う余地がある

**評価方針（保守的に扱うこと）**

価格差の収束を利益として織り込むと、収束しなかった場合に想定が崩れる。**デフォルトではベーシス項をゼロとして評価し、「価格差が不利な時は建てない」というフィルタとしてのみ使うこと。**

```rust
fn evaluate_funding_entry(ctx: &MarketContext, cfg: &FundingArbConfig) -> Option<TradeSignal> {
    let funding_gain_bps = rate_diff_bps * expected_intervals;
    // 建てる方向で価格差が有利(正)か不利(負)か。符号付きで計算する
    let basis_entry_bps = signed_basis_bps(long_dex, short_dex, symbol, ctx);

    // 不利なベーシスで建てない
    if basis_entry_bps < -cfg.max_adverse_basis_bps {
        return None;
    }

    // 保守評価: 有利なベーシスは利益に加算しない（収束を当てにしない）
    let basis_credit = if cfg.count_favorable_basis {
        basis_entry_bps.max(Decimal::ZERO)
    } else {
        Decimal::ZERO
    };

    let net = funding_gain_bps + basis_credit
            - total_fee_bps - slippage_bps - cfg.safety_buffer_bps;
    (net > cfg.min_profit_bps).then(|| /* TradeSignal */)
}
```

```toml
[strategy.funding_arb]
# これ以上不利なベーシスでは建てない（bps）
max_adverse_basis_bps = 2.0
# 有利なベーシスを期待収益に加算するか。デフォルトfalse（保守的）
count_favorable_basis = false
```

**手数料の回収可否**

手数料は**建てと決済で、両DEXそれぞれに発生する（計4回分）**。1精算あたりのレート差が手数料合計を下回る場合、**最低でも何回精算をまたぐ必要があるか**を計算し、それだけ保有し続けられる前提でなければシグナルを出してはいけない。

```rust
/// 手数料を回収するのに必要な最低精算回数
fn breakeven_intervals(rate_diff_bps: Decimal, total_fee_bps: Decimal) -> Option<u32> {
    if rate_diff_bps <= Decimal::ZERO { return None; }
    Some((total_fee_bps / rate_diff_bps).ceil().try_into().ok()?)
}
```

設定で `max_acceptable_breakeven_intervals`（例: 6回 = 6時間）を持ち、これを超えるシグナルは棄却する。

### 5.3 精算間隔の扱い

**HyperliquidとLighterはともに1時間精算**のため、フェーズ1〜2の範囲ではレートを直接比較してよい。

ただし将来のDEX追加に備え、**実装は最初から間隔の違いを扱える形にすること**:

- `FundingRate::interval_hours` を必ず参照する
- 異なる間隔のDEX同士を比較する場合は、年率換算（`annualized_pct`）で正規化する
- **精算タイミングがずれる場合の扱い**: 片方が毎時00分、もう片方が毎時30分に精算するなら、両方の精算を跨ぐには最低1時間必要になる。`next_funding_time_ms` を使って、両DEXの次回精算時刻を把握した上でエントリータイミングを決めること

### 5.4 エントリー・エグジットの設計

**エントリー**:
- `Urgency::Patient` を使う。IOCではなく**指値（メイカー）で建てる**ことで手数料を削減できる可能性がある
- ただし片側だけ約定するリスクは価格差アービトラージと同じ。既存の`HedgeState`状態機械をそのまま使い、片肺になったら即クローズする
- 指値で待つ場合、`BothPending`の滞在時間が長くなる。**価格差アービトラージ用のタイムアウト値をそのまま使わないこと**。戦略ごとにタイムアウトを設定可能にする

**エグジット判定** (`should_exit`):
以下のいずれかで解消する。

1. **レート差が消滅・反転した** — 保有理由がなくなった
2. **レート差が手数料を下回った** — 決済コストを払ってでも抜けるか、保有継続かを比較して判断
3. **最大保有期間に到達** — 設定で上限を持つ（例: 72時間）。長期保有は想定外リスクが蓄積する
4. **証拠金維持率の悪化** — リスク管理層からの指示
5. **キルスイッチ発動**

### 5.5 ファンディング裁定に固有のリスク

設計に必ず織り込むこと。

- **レート反転リスク**: 建てた直後にレート差が消えると、手数料だけ払って終わる。エントリー判定は「今のレート差」ではなく、**レート差がどれだけ持続してきたか**の履歴も見るべき（フェーズ1のファンディングCSVがここで効く）
- **長期保有中の証拠金リスク**: 両建てで価格中立でも、片方のDEXで含み損が膨らめば証拠金維持率が下がる。レバレッジなしでも、価格が大きく動けば片側の証拠金が圧迫される。**定期的な証拠金再配分（リバランス）が必要になる可能性がある**
- **資金拘束**: ポジションを長時間持つため、価格差アービトラージ用の証拠金と食い合う。**戦略ごとの証拠金枠を分離する**こと（後述）
- **精算時刻の集中**: 両DEXが同じ時刻に精算する場合、その瞬間に約定・レートが荒れる可能性がある

## 6. 資金配分（2戦略の共存）

### 6.1 証拠金枠の分離

2戦略が同じ証拠金プールを取り合うと、ファンディング裁定の長期ポジションが価格差アービトラージの機会を潰す（またはその逆）。

**戦略ごとに証拠金枠を分離すること。**

```toml
[allocation]
# 各DEXの証拠金プールに対する配分比率
price_arb_pct = 0.30      # 価格差アービトラージ用
funding_arb_pct = 0.40    # ファンディング裁定用
reserve_pct = 0.30        # 未使用バッファ（緊急クローズのスリッページ吸収用）
```

- 合計が1.0を超えないこと（起動時にバリデーションする）
- 各戦略は自分の枠を超えて発注できない
- `reserve_pct` は**どちらの戦略も使えない**。緊急クローズ専用の余力として常に確保する

### 6.2 既存のサイジングルールとの関係

既存の「1取引サイズは証拠金プールが少ない方の5%を上限」は、**価格差アービトラージに対するルール**として維持する。

ファンディング裁定は別途上限を設ける:

```toml
[strategy.funding_arb]
per_position_max_pct = 0.10       # 1ポジションあたり、funding_arb枠に対する比率
max_concurrent_positions = 4      # 同時保有ポジション数の上限
max_holding_hours = 72            # 最大保有時間
max_acceptable_breakeven_intervals = 6
min_rate_diff_bps = 1.0           # これ未満のレート差はシグナルを出さない
```

## 7. リスク管理（2戦略対応への拡張）

既存の多層キルスイッチ（`perp-arbitrage-bot-spec.md` §5）を、戦略ごとに独立して発動できるよう拡張する。

- **戦略レベルのキルスイッチを追加**: 片方の戦略だけを停止できること。価格差アービトラージが不調でも、ファンディング裁定は継続してよい場合がある
- **Bot全体レベル**（1日の最大損失額）は従来通り両戦略を止める
- **証拠金維持率の監視**は戦略横断で行う。ファンディング裁定の長期ポジションが維持率を圧迫している状況で価格差アービトラージが発注するのは危険

```toml
[killswitch]
# 戦略ごとに独立して停止できる
price_arb_daily_loss_limit_pct = 2.0
funding_arb_daily_loss_limit_pct = 2.0
# Bot全体（両戦略を停止）
global_daily_loss_limit_pct = 3.0
```

## 8. フェーズ計画の更新

### フェーズ1（現在）— 2 DEXでデータ収集

**対象: Hyperliquid + Lighter のみ**

- 板データ収集（既存の`phase1-design.md`通り）
- ファンディングレート収集（`funding-rate-collection-design.md`通り）
- edgeX / Aster は `enabled = false`

**このフェーズで検証すること（2戦略分）**:

| 戦略 | 検証項目 |
|---|---|
| 価格差 | 乖離幅の分布、手数料超えの発生頻度、**乖離の継続時間**（最重要）、staleness除外後に残る真の乖離 |
| ファンディング | レート差の分布、**レート差が同符号で持続する時間**（最重要）、手数料回収に必要な精算回数の分布、レート反転の頻度 |
| ファンディング（ベーシス） | ファンディング差が有利な瞬間の**価格差の分布**（両者は相関するはず。ファンディングが高いDEXは価格も高い傾向がある）、**一定時間内に価格差がどれだけ動くか**の分布 |

> **ベーシスの変動幅は特に重要**。これが大きいと、ファンディング収益が価格差の変動に埋もれる。既存のCSVで板データとファンディングの両方が取れているため、**追加実装なしで分析できる**。

> ファンディング側の「持続時間」は、価格差側の「継続時間」と同じくらい重要。レート差が1回の精算しか持たないなら手数料で消える。

### フェーズ2 — ドライラン（実弾なし）

- 両戦略のシグナル生成ロジックを実装し、**シグナルのみ記録**
- 価格差: 検知から発注が間に合ったであろう割合を推定
- ファンディング: シグナル通りに建てていたらどうなったかを、収集済みレート履歴で事後評価

### フェーズ3 — testnetで機能検証

- 発注・状態機械・緊急クローズ
- **ファンディング裁定は`Urgency::Patient`の指値執行パスも検証すること**（価格差用のIOCパスとは別経路）

### フェーズ4 — 本番導入

- **ファンディング裁定から先に実弾投入することを推奨**。速度要求が低く、個人環境でも構造的に成立しやすいため、検証結果が読みやすい
- 価格差アービトラージは、フェーズ1〜2の実測で「間に合う」と判断できた場合のみ実弾へ

## 10. 実装順序

## 11. 実装前に確認すべき事項

- **HyperliquidとLighterの精算間隔が本当に両方1時間か**、一次情報で再確認（本書の前提が崩れると設計全体に影響する）
- 両DEXの**精算タイミング**（毎時何分に精算されるか）。ずれている場合、エントリー設計に影響する
- 両DEXの maker / taker 手数料率（ファンディング裁定では指値執行でメイカー手数料になる可能性があるため、両方必要）
- ファンディングレートの**符号の規約**が両DEXで同じか（正 = ロングが支払う）
- Lighterで指値注文（メイカー執行）が可能か、およびその発注APIの仕様
